# Roles, Permissions and Plans

The authorization model, in full. Every table here was generated by executing
the enum methods, not transcribed by hand — if this document and the code
disagree, the code wins.

## 1. One axis

The application has **one** authorization system. An account's authority
everywhere in the product is described by a single pair of enums:

```
Account
───────────────────────────
user / seller / admin
platform-wide
stored on users.role
```

It answers one question: *what may this account do on this platform?* May it
publish posts? May it create product listings? May it open the admin panel?

> **Historical note.** The starter kit this project began from carried a second,
> narrower axis — team roles (`owner`/`admin`/`member`) on `TeamRole`, resolved
> against a `Membership` row. That whole feature was **removed**: there is no
> team, no membership, and no second role to reconcile against. Any earlier
> revision of this document that described a two-axis model is obsolete. Removing
> the second axis also removed the class of bug it was there to prevent, because
> a team-scoped role is no longer expressible at all.

## 2. Account roles

| Role | Level | Permissions | Plan |
| --- | --- | --- | --- |
| `user` | 1 | 6 | `free` |
| `seller` | 2 | 15 | `seller` |
| `admin` | 3 | 28 | `platform` |

Roles are **additive by construction**:

```php
// AccountRole::Seller
public function permissions(): array
{
    return [
        ...self::User->permissions(),   // inherits all six
        AccountPermission::PublishPost,
        // … eight more
    ];
}

// AccountRole::Admin
public function permissions(): array
{
    return AccountPermission::cases();   // everything
}
```

**Seller inherits by spread.** Adding a permission to `User` automatically
reaches `Seller`. This is intended: a seller *is* a user with more.

**Admin returns every case.** A new permission is granted to admins the moment
it is declared. Also intended: an admin is *defined* as "can do everything",
not as a list someone must remember to update.

The consequence to be aware of: **there is no way to give an admin a permission
without giving it to all admins.** That is the point, but it means "an admin who
cannot do X" is not expressible — a different role would be needed.

### Level and comparison

`level()` returns 1, 2 or 3. `isAtLeast(AccountRole $other)` compares them.

Level is used for **ordering**, not for authorization. Authorization always
goes through `hasPermission()`. A `level()` comparison is appropriate for "may
this actor act on this target" (a 3 may act on a 1 or a 2) and inappropriate for
"may this actor publish a post" — use the permission for that.

## 3. The permission matrix

28 permissions in 5 groups. The right-hand column lists the roles that hold
each.

### Content — 6

| Permission | `user` | `seller` | `admin` |
| --- | :---: | :---: | :---: |
| `post:create` | ✓ | ✓ | ✓ |
| `post:update-own` | ✓ | ✓ | ✓ |
| `post:delete-own` | ✓ | ✓ | ✓ |
| `post:update-any` | | | ✓ |
| `post:delete-any` | | | ✓ |
| `post:publish` | | ✓ | ✓ |

**`post:publish` is not granted to `user`.** This is the sharpest restriction in
the model and worth dwelling on: a plain user can *write* a post and can *edit*
their own post, but cannot make it public. Publishing requires at least a seller
role.

That is a product decision, not an oversight — it means an ordinary account
cannot put arbitrary content on the public site. Anyone permitted to author must
also be trusted to publish.

### Moderation — 2

| Permission | `user` | `seller` | `admin` |
| --- | :---: | :---: | :---: |
| `comment:moderate` | | | ✓ |
| `taxonomy:manage` | | ✓ | ✓ |

Comment moderation — approving and rejecting — is **admin-only**. Sellers may
manage taxonomy (categories and tags) because product listings need them.

### Platform — 3

| Permission | `user` | `seller` | `admin` |
| --- | :---: | :---: | :---: |
| `dev-lab:use` | ✓ | ✓ | ✓ |
| `ai-hub:use` | ✓ | ✓ | ✓ |
| `ideas:use` | ✓ | ✓ | ✓ |

The three modules every account may reach. Each guards one top-level route —
`/dev-lab`, `/ai-hub`, `/ideas` — which currently renders a placeholder page
stating the module is not yet available. The route and the permission are real
now so the URL space is claimed and the navigation works; only the module bodies
are outstanding.

These are **baseline** permissions: they sit in `AccountRole::User` and are
inherited upward by spread, so every role holds them. That is intentional — a
developer tool and an ideas backlog are not privileges, and gating them would
mean a seller loses a capability the moment they are promoted past `user`.

### Selling — 7

| Permission | `user` | `seller` | `admin` |
| --- | :---: | :---: | :---: |
| `marketplace:use` | | ✓ | ✓ |
| `product:create` | | ✓ | ✓ |
| `product:update-own` | | ✓ | ✓ |
| `product:delete-own` | | ✓ | ✓ |
| `product:submit` | | ✓ | ✓ |
| `sale:view-own` | | ✓ | ✓ |
| `support:manage-own` | | ✓ | ✓ |

This group is **the seller role's reason to exist**. Every permission is
`-own` or `:create` — a seller operates on their own inventory and nobody
else's. The `-any` counterparts live in the Administration group.

`marketplace:use` guards `/marketplace`, the Developer Marketplace &
Digital Product Ecosystem module. It is the one module gated **above** the
baseline: browsing and selling in a marketplace is the seller's function, so a
plain `user` does not reach it. The page is a placeholder for now.

> **Not implemented.** The six `product:*` / `sale:*` / `support:*` permissions
> are fully defined and enforced by the middleware, but there is **no `Product`
> model** to authorize against. The seller dashboard is reachable and its sidebar
> entries filter correctly; the listings page does not exist. See
> [`audit/PHASE-0-AUDIT.md`](audit/PHASE-0-AUDIT.md) §10.

### Administration — 10

| Permission | `user` | `seller` | `admin` |
| --- | :---: | :---: | :---: |
| `admin:access` | | | ✓ |
| `user:manage` | | | ✓ |
| `role:manage` | | | ✓ |
| `product:review` | | | ✓ |
| `product:manage-any` | | | ✓ |
| `seller:manage` | | | ✓ |
| `sale:view-any` | | | ✓ |
| `refund:process` | | | ✓ |
| `payment:configure` | | | ✓ |
| `audit:view` | | | ✓ |

Note that `admin:access` — the permission guarding the whole `/admin` sub-tree —
is itself a permission rather than a role check. A route declares
`permission:admin:access`; nothing anywhere declares `role:admin`.

**Why no `role:admin` check exists.** A route guarded by role name must be
edited every time that role's permissions change, and a "temporarily grant one
admin this one thing" request becomes a code change. Permission guards make the
permission the unit of authorization throughout.

## 4. Plans

`RolePlan` is **commercial**, not authorization. A plan describes what an
account is *entitled to buy or be limited by*; a role describes what it may
*do*.

| Plan | Plan key | Listing limit | Commission | Can sell |
| --- | --- | --- | --- | --- |
| Free | `free` | 0 | — | ✗ |
| Seller | `seller` | 25 | 15.0% | ✓ |
| Platform | `platform` | unlimited (`null`) | 0.0% | ✓ |

| Role | Default plan |
| --- | --- |
| `user` | `free` |
| `seller` | `seller` |
| `admin` | `platform` |

**Why plans are separate from roles.** They change for different reasons and at
different rates. A role is a code change; a plan is a business decision — a
promotional listing limit, a different commission band, a trial. Modelling them
in one enum would mean every pricing change is an authorization change.

`productListingLimit()` returns `null` for unlimited and `0` for "not allowed".
Those are genuinely different states and the distinction is preserved rather
than collapsed into a falsy value.

## 5. Enforcement

Authorization is checked at **three** levels. All three matter.

### Level 1 — Route middleware

```php
Route::middleware(['auth', 'verified', 'permission:'.AccountPermission::AccessAdminPanel->value])
    ->prefix('admin')
    ->name('admin.')
    ->group(function () {
        Route::livewire('dashboard', 'pages::admin.dashboard')->name('dashboard');
        Route::livewire('users', 'pages::admin.users')->name('users');
    });
```

`EnsureAccountPermission` refuses the request before the component boots, so an
unauthorised account gets a `403` rather than a rendered shell with hidden
buttons.

```php
Route::middleware('permission:post:create');                    // any single
Route::middleware('permission:user:manage,role:manage');        // OR — either grants
Route::middleware('permission:all:user:manage,role:manage');    // AND — both required
```

Three behaviours worth stating explicitly:

- **The default is OR.** `permission:a,b` means *a or b*. It does not tighten.
- **A guest is redirected to login, not refused.** They may hold the permission
  once authenticated; a `403` would be a dead end.
- **A route with no valid permission aborts `500`.** `abort_if($required === [],
  500, 'Route declares no valid permission.')` catches a typo'd alias, because
  a guard that silently allows everything is the worst possible failure.

### Level 2 — Policies

Route middleware cannot answer "may this account edit **this** post" — the model
is not bound until the component runs. Policies do.

| Policy | Methods |
| --- | --- |
| `PostPolicy` | `viewAny`, `viewPublic`, `view`, `create`, `update`, `delete`, `restore`, `forceDelete`, `publish` |
| `UserPolicy` | `viewAny`, `view`, `updateRole`, `update`, `delete` |

Two methods deserve comment:

- `PostPolicy::viewPublic` is separate from `view` because the two audiences are
  different: `view` answers "may the dashboard show this post", `viewPublic`
  answers "may the public route serve it". A draft is `view`-able by its author
  and never `viewPublic`-able by anyone.
- `UserPolicy::updateRole` is the escalation guard (see §6), and it is the
  policy that replaced the removed `TeamPolicy` as the place where "who may
  administer whom" is decided.

`UserPolicy::updateRole` is the escalation guard, and it is checked twice:

```php
// 1. The policy authorizes the action.
Gate::authorize('updateRole', User::class);

// 2. The enum filters which roles the actor may grant.
$assignable = AccountRole::assignableBy(auth()->user()->accountRole());
```

Redundant on purpose. Privilege escalation is the one bug class worth defending
twice.

### Level 3 — Model

`HasAccountRole` puts the questions on the model, so blade templates and actions
never reach for a service:

```php
$user->hasPermission(AccountPermission::CreatePost);
$user->hasAnyPermission(...);
$user->hasAllPermissions(...);
$user->isSeller();
$user->canAccessAdminPanel();
$user->canActOn($other);          // other-account safety
```

## 6. Role assignment

`AccountRole::assignableBy($actorRole)` returns the roles an actor may grant.

| Caller | May assign |
| --- | --- |
| `user` | `user` |
| `seller` | `user`, `seller` |
| `admin` | `user`, `seller` |

Two rules are encoded:

1. **Never at or above your own level.** `user` cannot grant `seller`; `seller`
   cannot grant `admin`.
2. **`admin` is assignable by nobody.** `filter(fn ($role) => $role !==
   self::Admin)`.

Rule 2 exists so that a compromised admin token or session cannot be used to
**mint more admins**. Without it, one escalation becomes permanent and
unbounded.

> **Consequence: there is no in-application path to admin.** The admin role is
> reachable only through `UserSeeder` or a direct database write. On a fresh
> deployment that is a bootstrap problem — the first admin cannot be created
> through the UI. This needs a deliberate answer (an artisan command, or a
> config allow-list) before the system is operated by anyone but its author.
> Recorded in [`audit/PHASE-0-AUDIT.md`](audit/PHASE-0-AUDIT.md) §10.

`UserPolicy::updateRole` additionally refuses an actor acting on a peer or
superior:

```php
$target->accountRole()->isAtLeast(auth()->user()->accountRole())
```

So an admin cannot demote another admin through the UI, even though the enum
would permit granting `seller`.

## 7. Navigation

`app/Support/DashboardNavigation.php` is the single definition of the dashboard
sidebar. Each entry declares the permission its route requires:

```php
[
    'label'       => 'Comments',
    'route'       => 'dashboard.comments',
    'pattern'     => 'dashboard/comments',
    'icon'        => 'chat-bubble-left-right',
    'permissions' => [AccountPermission::ModerateComments],
    'badge'       => self::BADGE_PENDING_COMMENTS,
]
```

`for(User $user)` filters by permission, and **both the nav and the route guard
read from this one source**. A menu item therefore cannot be visible to an
account whose route would refuse it.

Before this existed, a nav link and its route guard were two separate statements
of the same rule, and they drifted. The failure is silent: a link that 403s, or
worse, a page reachable by URL that no menu reveals.

**Badges are resolved, never leaked.** `BADGE_PENDING_COMMENTS` is a sentinel
resolved to an `int` inside `for()`. An earlier version passed the sentinel
string through to the markup; it also failed PHPStan's return-type check, which
is how it was caught.

`pendingCommentCount()` scopes to the account's own posts unless the account
holds `comment:moderate` — so an author sees pending comments on their writing,
and an admin sees all of them.

## 8. Testing authorization

**Test the denial path for every grant.** The interesting failures are all
negative.

```php
test('a plain user cannot reach the admin dashboard', function () {
    $user = User::factory()->create();          // defaults to `user`

    $this->actingAs($user)
        ->get(route('admin.dashboard'))
        ->assertForbidden();
});
```

Factory states make each role one line:

```php
User::factory()->create();                  // user
User::factory()->seller()->create();
User::factory()->admin()->create();
User::factory()->role(AccountRole::Seller)->create();
```

**What is covered.** `tests/Feature/Enums/PermissionModelTest.php` pins the
**composition** of every role's permission set — not just its size. A count
assertion catches a permission being added or removed; it does not catch one
being silently swapped for another of the same group, which is the change that
would quietly let a plain user publish. Specific behaviours are asserted
individually:

- a plain `user` cannot publish; a `seller` can
- comment moderation is admin-only
- seller inherits every user permission by construction
- admin holds every declared permission
- every permission resolves to a group, and grouping loses nothing
- no role may grant a role at or above its own level, and `admin` is not
  assignable by anyone
- `RolePlan::Platform->productListingLimit()` is `null` (unlimited), not `0`
- every role reaches the three baseline modules; the marketplace is seller-and-above
- each role owns a distinct top-level dashboard route

`DashboardTest` asserts role-scoped dashboards, sidebar filtering, role badges
and `dashboardRoute()` per role. `RoutingStructureTest` asserts the route shape
directly: the three role paths are distinct and unnested, each role reaches only
its own dashboard, guests are redirected to login rather than refused, the four
module routes exist and are permission-gated, the old nested paths return `301`,
and **no registered route carries a `team` or `current_team` parameter** — the
regression test for the removed feature. `Dashboard/ModerationTest` asserts that
comments on another author's posts are never listed — a negative assertion, which
is the only kind that would catch a missing scope.

These tests were written against a first draft of this document and **caught two
errors in it** (comment moderation is admin-only rather than seller-accessible,
and a permission-group total did not match the enum). That is the argument for
pinning composition: prose drifts silently, tests do not.

## 9. Extending the model

### Adding a permission

1. Add the case to `AccountPermission`.
2. Implement `group()` for it — an unhandled case is a PHPStan error, which is
   deliberate: a permission with no group cannot be rendered in grouped UI.
3. Add it to `AccountRole::User` if **every** role should hold it (a baseline
   module like `dev-lab:use`), or to `AccountRole::Seller` if sellers and above
   should hold it.
4. **Nothing else.** Admins receive it automatically from `cases()`.

If the permission guards a route, add the route beside its siblings in
`routes/web.php` and an entry in `DashboardNavigation` — the nav and the guard
must read from the same permission, or a link can 403.

### Adding a role

1. Add the case to `AccountRole` and implement `label()`, `description()`,
   `badgeColor()`, `plan()`, `permissions()`, `level()`, `dashboardRoute()`.
2. Add a `RolePlan` case, or return an existing plan.
3. Create `resources/views/pages/<role>/⚡dashboard.blade.php`, with
   `#[Layout('layouts::dashboard')]` on the component — the Livewire default
   layout is the public shell.
4. Add a middleware-guarded group in `routes/web.php`, using a **permission**
   guard rather than a role check.
5. Add `DashboardNavigation` entries.
6. Add a `UserFactory` state and a `UserSeeder` account.

Step 3 is the minimum for the role to *work*: `RedirectsToRoleDashboard` uses
`router->has()` so a role can be declared before its dashboard exists, and login
falls back to `/dashboard` rather than producing a 500.

### Changing what a role can do

Edit exactly one method: `AccountRole::<role>()->permissions()`. Every guard,
every sidebar entry and every policy follows. There is no cache, no database
row and no config to invalidate.
